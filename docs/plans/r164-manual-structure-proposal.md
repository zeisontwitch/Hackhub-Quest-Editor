## 1. Structure decision — a small set of linked static pages

**Recommendation: `public/manual/` with one HTML file per page, sharing one CSS
file and one JS file. No framework, no static site generator, no new
dependency, no build step for the pages themselves.**

The reasoning, in one paragraph as required:

The full manual is roughly **57,000 words** (breakdown in §3). Of that,
~30,000 words are the node reference — 120 field entries at ~110 words each,
65 port entries, and 34 × ~400 words of surrounding page furniture. A single
file at that size is not editable: every one-word fix touches a ~40,000-line
document, review diffs become unreadable, and no reviewer can hold it in their
head. A directory of small pages costs nothing extra in tooling — each file is
plain HTML opened or linked to directly, exactly like `manual.html` is today —
and it makes the coverage gate trivial, because "does node `fx.pay` have a
page" becomes "does `nodes/fx-pay.html` exist and contain its field anchors".

The one real constraint is H1 (self-contained, offline, opens from disk).
Client-side **search across pages** cannot use `fetch()` on `file://` — browsers
block it. It *can* use a plain `<script src="search-index.js">`, which is not
subject to the same restriction. So the manual ships one generated
`search-index.js` holding every page's title, anchors and a text digest, and
every page loads it with a script tag. Offline ✓, opens straight from disk ✓,
one source of truth ✓, and because it is generated by the same script that
checks coverage it cannot drift.

**H12 — the existing delivery mechanism is preserved.** `public/manual.html`
stays, reduced to a redirect to `manual/index.html`. Vite keeps copying
`public/` verbatim, so `dist/manual.html` still resolves for anyone who
bookmarked it.

```
public/manual/
  index.html            Start here + the nav shell
  tutorial.html         Your first quest
  concepts.html         Core concepts
  nodes/<type>.html     34 files, one per obtainable node type
  guides/<feature>.html 10 files, one per feature surface
  how-do-i.html          All recipes on one page (they are short and cross-link)
  checking.html         Every message the editor can show
  export.html           Exporting and installing
  troubleshooting.html  Decision tree + FAQ
  appendices.html       Glossary, shortcuts, limits, version stamp
  manual.css            Theme-matched to the editor (read from src/index.css)
  manual.js             Nav, TOC highlighting, search, collapse, print — vanilla
  search-index.js       Generated. Every page's titles, anchors and digest
  img/                  Screenshots (placeholders this round, per your call)
```

Old anchors: today's 33 section-level ids (`#intro`, `#nodes`, `#n-flow`, …) get
carried into `index.html` as redirect aliases so nothing that links to them
silently breaks.

## 4. Controlled vocabulary (V11)

One term per concept, forever. The left column is the only word the manual uses.

| Concept | The manual says | Never |
|---|---|---|
| A block on the canvas | **node** | block, box, element, tile |
| A link between nodes | **wire** | edge, connection, link, line |
| The round thing you drag from | **socket** | port *(reserved for the game's network ports)*, handle, pin, dot |
| The whole thing being built | **your quest** | project *(except for the saved file)*, mod *(only for the exported zip)* |
| The saved file | **project file** | document, JSON, save |
| The exported result | **the mod** / **the .zip** | build, output, package |
| Making the zip | **Export** | compile, build, generate, package |
| The panel on the right | **inspector** | sidebar, properties, panel |
| A row in the inspector | **field** | input, control, property |
| The grey sentence under a field | **hint** | tooltip, description, blurb |
| A warning or error | **message** | issue *(except when quoting the UI)*, diagnostic |
| The play-through before export | **Dry run** | simulate, test, preview |
| What the player must do | **objective** | task, goal, mission |
| A thing that happens in the game | **event** | trigger *(the socket is the Trigger; the thing is the event)* |
| The people in the story | **NPC** or the character's name | entity, actor |

**Word collisions the glossary owns explicitly:**

- **node** — a block on your quest map. In the game's own fiction a "node" can
  also mean a machine on a network; in this manual it always means the block.
- **port** — a socket on a node is never called a port in this manual. "Port"
  always means a network port (22, 80), the thing `nmap` reports.
- **quest** — the thing you are building. The game also uses "quest" for its own
  story missions; where that matters the manual says "the game's own quests".
- **trigger** — the socket named **Trigger** on an Objective node. The event
  that fires into it is an event, not a trigger.

## 7. Answering the maintenance worry

Your concern is the right one, and "the coverage test will catch it" is too thin
an answer on its own. Here is the actual mechanism.

**The rule that makes 52 files safe: you never go looking for what changed.
`npm test` tells you the file and the line.** The gate reads the registry and
every file under `public/manual/`, diffs them, and fails with a message that
names the file. Splitting the manual does not add anything you have to remember
— it makes the failure *smaller and more precise*, because the fix is one file
instead of a search through a 40,000-line document.

### The nine gates

| # | Fails when | Example failure message |
|---|---|---|
| G1 | a registry node type has no page, **other than the one on the exclusion list** (`world.wifi`) | `manual: node type "fx.setData" has no page at nodes/fx-setdata.html` |
| G2 | a field key has no entry on its node's page | `manual: world.port field "Version" has no "### Version" heading in nodes/world-port.html` |
| G3 | a documented node or field no longer exists | `manual: nodes/flow-delay.html documents field "millis", which world… is not on flow.delay any more` |
| G4 | an anchor the app links to is gone | `manual: anchor #node-fx-pay missing, referenced from InspectorPanel.tsx` |
| G5 | an internal link points nowhere | `manual: how-do-i.html links to checking.html#msg-dead-end, which does not exist` |
| G6 | a banned word appears in the body | `manual: concepts.html:88 uses "compile"; the UI word is "Export"` |
| G7 | a message string has no index entry | `manual: compile.ts emits "…Kisscord uploads compile to…" with no entry in checking.html` |
| **G8** | **an image is missing or orphaned** | `manual: nodes/fx-pay.html references img/node-fx-pay-inspector.png, which is not in public/manual/img/` |
| **G9** | **a quoted UI string no longer exists** | `manual: tour-workspace legend says "Dry run"; no such string in src/editor/**` |

G8 is what makes your screenshot workflow safe: capture in any order, over as
many sittings as you like, and the build tells you exactly which files are still
wanted. G9 is what catches a renamed button — the class of drift that silently
makes a manual lie.

### What changed → what breaks

| Someone changes… | The gate that fires | You touch |
|---|---|---|
| adds a node type | G1 | one new `nodes/<type>.html` |
| renames a field label | G2 + G9 | one heading in one page |
| removes a field | G3 | one section in one page |
| rewords a validation message | G7 | one entry in `checking.html` |
| renames a button or menu item | G9 | every page quoting it (the message lists them) |
| changes a default or a limit | **nothing** | see below |
| adds a theme or a font | **nothing** | `guides/settings.html` |

### The honest limit

Gates catch *missing* and *renamed*. They cannot catch **prose that went
wrong while the label stayed the same** — a field whose behaviour changed but
whose label did not trips nothing, because the manual still has a `### Version`
heading and the string `Version` still exists in the source.

Two things cover that gap, and neither is automatic:

1. **The maintenance note** (Phase 6) states the standing rule: changing a node
   type, field, label, info blurb or message requires updating the manual *in
   the same round*. The gate enforces the structural half; the note is the
   human half.
2. **Defaults and limits come from the schema, not from prose, wherever
   possible.** NR3 already requires it. Where a page can show the range as
   `0–65535` because the registry says `min: 0, max: 65535`, a changed limit is
   a wrong number on the page rather than a plausible sentence — and a reviewer
   checking one page against one registry entry will see it.

So: 52 files, and the build is the thing that remembers. That is a better
position than one file, where the same gate would fire and you would still have
to find the needle.
