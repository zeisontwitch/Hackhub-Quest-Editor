Exporting and installing

Turning your project into a mod the game can play, what is inside the file it gives you, and what to do with it afterwards.

Exporting is the last step. It reads everything you built — the quests, the websites, the machines — and packs it into a .zip the game loads as a mod. Nothing about your project changes when you do it, and you can export as often as you like.

Exporting also runs the second set of checks, the ones that need the whole mod in front of them rather than one node at a time. Read the report before you download, because some of what it finds means the game will quietly drop something you built.

The export window

Opening the export window shows you what you are about to ship before it is packed. Its own words for the job:

Compiles everything into a ready-to-play mod folder — no coding needed. Unzip it into the game's mods/ directory.
Quests
Every quest in the project, by title. If a quest is missing from this list, it is not in the mod either.
Websites
Every host your mod registers. Worth a look, because domains belong to the whole game and two mods claiming one host will fight over it.
Permissions requested
The list below. The game shows these to the player when they install, so a shorter list is a friendlier one.
In the zip
Every file that will be packed, by path. Nothing is hidden from you here.
Needs attention
Red — at least one export check found something the game will drop or change. Fix it before you download.
Good to know
Amber — the export shipped what you built, and what you built may not be what you meant.

The seven permissions

A permission is a promise about what your mod touches. You do not pick them anywhere: the editor works out which ones your nodes need and asks for exactly those. Delete the node and the permission goes with it.

PermissionAsked for byWhat it lets the mod do
networkCreate network · Register domain · Create database · Place filesPut machines, names and files into the game's world.
filesystemPlace filesWrite files onto the player's own machine.
shellRun terminal command · Tool response · Manual inputRun commands, answer for the game's tools, and add a command of your own.
eventsWhen event · Claim another questWatch for what the player does, and start another quest.
mailDialogue, with Mail as the kind · a {{player.email}} tokenSend messages to the player's mail app, and read their address.
bankPay the player · Charge the playerMove money in and out of the player's account.
uiNotifyPut a message on the player's screen.

The plain words behind each one are in Permissions, in plain words.

What is in the .zip

Two of these files are the mod. The rest are there so that somebody who wants to change the mod later can rebuild it, and so the folder makes sense to anyone who opens it. You never need to touch any of them.

FileWhat it is
dist/mod.jsThe mod. Everything you built, turned into something the game can run.
manifest.jsonThe mod's card: its name, author, description, version and the permissions it asks for. This is what the game reads first.
dist/manifest.jsonA second copy of the card, where the game also looks for it.
README.mdA short description of the mod, with its permissions and any warnings the export produced.
src/index.tsThe same mod as dist/mod.js, in the form a developer would edit.
package.jsonBuild instructions, for anyone rebuilding the mod from src.
esbuild.config.mjsThe tool that turns src into dist.
tsconfig.jsonSettings for the same rebuild.
You do not need any of this to ship a quest. The editor builds the whole folder for you. It is listed here so the export window is not a list of unexplained filenames.

Installing it

The file downloads with a name built from your mod's identifier and version, so meridian-1.0.0.zip is version 1.0.0 of the mod called meridian. Two versions of one mod therefore never share a filename, which matters when you are testing a change against the last one.

  1. Open the export window and read the report. Fix anything red.
  2. Choose Download .zip. The button reads Packing… while the file is built.
  3. Unzip the folder into the game's mods/ directory, as the export window tells you. The folder inside the archive is the mod; the archive itself is not.
  4. Start the game. The mod is loaded, and its quests are available to accept.
Unzip it, do not drop it in whole. The game reads a folder in mods/, not an archive. A .zip sitting in that directory is ignored.

Export is not a save

This is the mistake worth understanding properly, because it loses work. The .zip is the finished mod. It is the thing the game plays, and it is not something you can open in the editor and carry on editing.

Your project file is the editable thing. It holds your canvas, your node settings and your websites in the form the editor understands. Saving keeps that up to date; exporting only produces a copy for the game to run.

To keep working
Save the project, and open the project again next time. Not the .zip.
To ship a change
Edit the project, then export again. The new .zip replaces the old folder in mods/.
If you only have the .zip
The quests inside it still play, but the canvas you built them on is gone. There is no way back from the mod to the project.

The build stamp

Every export writes the editor's own build into dist/mod.js, as 2026-09-19.r206. It is how you tell which version of the editor produced a mod, which is the first thing worth knowing when a quest behaves differently for someone else than it does for you.

The same stamp is in the footer of every page of this handbook, so you can check that the handbook you are reading describes the editor you are using. A handbook for an older build can describe a field that has since moved.

When you report a problem, give the build. Open any .zip you exported and the stamp is at the top of dist/mod.js. It saves everyone a round of questions.
