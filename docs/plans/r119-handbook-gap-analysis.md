# The in-game handbook, and what it changes

Zeis hand-copied the entire in-game handbook into
[`docs/In-Game-Handbook.md`](../In-Game-Handbook.md) — 4,102 lines, ~80
sections. It is the game's own teaching material, so it outranks the SDK for
*how a player is expected to work*, and it outranks the web entirely.

This is what it settles, what it changes, and where the editor falls short.

---

## 1. It answers questions we had open for dozens of rounds

### Phishing is fully documented — and my plan was wrong about it

I had gated the phishing template on an in-game test, unsure whether a mod
could produce a harvester attachment. The handbook describes the whole loop,
and the answer is that **the attachment is not something a mod authors** — it
is generated by Metasploit inside the game:

```
apt-get install metasploit
msfconsole
search office_word_macro
use exploit/multi/fileformat/office_word_macro
set payload bearos/meterpreter/reverse_tcp
set LHOST <your ip>
set LPORT <your port>
run          # creates the malicious document
handler      # starts the listener
```

Then the player delivers it *"using the mission's intended in-game
phishing/mail route"*, and the victim opening it triggers the reverse TCP
connection.

Two more constraints I would have got wrong:

- **The listener port must be forwarded on the router** the player is connected
  to, or the payload cannot call back. The handbook is explicit.
- **Current builds enforce that the player actually owns the file** before it
  can be attached to satisfy a delivery objective.

So a phishing template's job is to *set the stage* — a victim who will open the
document, a reason to send it — and to trigger on `Mail.Sent` and the resulting
`Metasploit.Meterpreter.Connected`. That is buildable today.

### Suspicion is real, game-native, and log-driven

Our dev-questions doc has *"no logging or suspicion API exists anywhere in the
SDK; possibly game-native"*. The handbook confirms it is game-native and
explains the mechanic precisely:

- Suspicion rises from incomplete or incorrect actions while hacking or
  phishing.
- **After getting a shell you are expected to find the access logs and delete
  the one line recording your shell — and leave the others alone**, because
  missing logs are themselves noticed.
- It falls again by changing the Wi-Fi network you are connected to (new IP and
  DNS).
- At 50% you can be hacked back; at 100% the federal authorities take
  everything.

This also explains the "empty `sys.log`" QA saw: logs are a *player-facing
mechanic*, and the game populates them.

### Logs have real paths

`/logs/accounts.log` for accounts created in a system, `/root/logs/terminal.log`
for terminal history. Both are things a quest could seed or reference.

### The router / firewall chain works as I guessed, but more precisely

My Cold Storage sketch assumed opening a router port makes a machine behind it
reachable. Confirmed, with the exact model: a forwarding rule is
**external port → internal IP → internal port**, and a rule that exists but is
disabled does nothing. There is a whole section on why a connection still fails
after you "opened the port" — the firewall sits in front of the router.

Our schema already models this correctly: `NetworkPort` has `external`,
`internal` and `active`, and `FirewallRule` has `port`, `source`, `destination`
and `allowed`.

## 2. Tool coverage: better than I expected

Cross-checking every tool the handbook teaches against the 92 events in
`reference/hackhub-events.json`, and the trigger node is populated from that
file, so **an author can already build an objective around almost all of them**:

| Handbook tool | Trigger event |
|---|---|
| nmap, whois, nslookup, mxlookup, dig, lynx, geoip | all present |
| metasploit (9 events incl. `Use`, `Event.Try`, `Rootgrab`) | present |
| hydra, john, hashcat, fern | present |
| bettercap (6 events), wireshark | present |
| sqlmap, nuclei, subfinder, dirhunter | present |
| ssh, ftp, files, mail, twotter, kisscord, weechat | present |
| python3 | present |

**Gaps, all minor:**

- `dnshistory` is taught but has no event. Nothing to trigger on.
- `scp` has no event of its own — `Files.Transfer` may cover it.
- Goagle, Netrun, Notepad, git/pip/node have no events. Mostly they are places
  the player reads things rather than actions a quest reacts to.

None of these block a template. They belong in the dev-questions doc.

## 3. Where the editor genuinely falls short

Zeis: *"Our node editor has to be able to utilize everything described in
there, in the way it is described."* Measured against that:

**We can express the events. We cannot always express the setup.**

1. **Router port-forwarding is not a first-class node.** A port has `external`
   and `internal` numbers on a device, but the handbook treats forwarding as a
   *rule on the router pointing at a child device* — external port, internal
   IP, internal port, enabled. An author following the handbook would look for
   that and not find it.

2. **Nothing seeds a log file the player is meant to clean.** The Suspicion
   mechanic hinges on finding an access log and deleting exactly one line. We
   can seed files, but there is no notion of "the log line that records your
   shell", and no way to react to it being cleaned.

3. ~~**`world.files` cannot put a file on a remote device**~~ — **fixed in
   r120.** The node now folds its files into the device's owning user at build
   time, which is the one mechanism that actually places a file on a remote
   machine (`NetworkUser.files`, mounted before anyone connects). A runtime fix
   was impossible: every `Files.*` call in the SDK resolves against the current
   session and none takes a target address.

4. **No node models the Metasploit payload/handler setup.** For a phishing
   quest the author needs the player to set `LHOST`/`LPORT`, forward that port,
   and run a handler. We can trigger on `Metasploit.SetOption`, so the
   objectives are expressible, but there is no guidance in the editor.

5. **The handbook's tool vocabulary is not in the editor's copy.** Field hints
   say "run whois"; the handbook teaches a *sequence* — whois, then nslookup,
   then dig, then subfinder. Templates are where that sequence should live.

## 4. What I would change, in order

1. **Un-gate the phishing template** and rewrite it against the documented
   flow: victim, lure, `Mail.Sent`, port forward, `Meterpreter.Connected`.
   It is no longer speculative.
2. **Add a Suspicion beat to the expert template.** Get the shell, find the
   access log, delete the right line. That is the game's own teaching, and no
   template shows it.
3. **Port-forwarding as a first-class node** (or at minimum a Router preset on
   the network node with the three fields the handbook names).
4. ~~**Revisit `world.files` on a remote device**~~ — done, r120.
5. **Fold the handbook's workflows into the templates**: the "I have a domain"
   and "I have an IP" chains are exactly the shape a good template should have.
6. **Update the dev-questions doc** — remove the Suspicion question, which is
   now answered, and add the `dnshistory` / `scp` event gaps.

## 5. Honest note on what this cost me

Three things in my r117 plan were guesses that the handbook contradicts or
sharpens: the phishing attachment (wrong — Metasploit makes it), the port
forward requirement (missed entirely), and the Suspicion mechanic (I had it
filed as "possibly game-native, unconfirmed" when it is documented in detail).

The handbook should be the first thing consulted for anything about how a
player is expected to *act*. The SDK says what a mod can call; the handbook
says what the game teaches. They are different questions and I had only one of
them.
